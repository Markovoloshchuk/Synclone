# Synclone — Синхронізатор пам'яті для клонів

**Data-Intensive Application (DIA)** на Python (FastAPI + SQLAlchemy).

---

## 1. Вибір предметної області та обґрунтування

Обрано **варіант 6 — «Синхронізатор пам'яті для клонів»**.

### Суть предметної області

Система забезпечує **безперервний потік створення бекапів свідомості мільйонів мешканців**.
Кожен клон періодично відправляє знімок своєї пам'яті (свідомості) до централізованого
сховища, а система має прийняти цей потік, зберегти метадані, поставити повні бекапи в
чергу подальшої обробки та віддати дані за запитом (відновлення, аналітика, порівняння
клонів). Основна проблема галузі — **великий обсяг даних і висока швидкість їх зміни**.

### Чому це саме Data-Intensive Application

| Вимір («3 V»)            | Прояв у цій предметній області                                                                                                  |
|--------------------------|----------------------------------------------------------------------------------------------------------------------------------|
| **Volume** (обсяг)       | Мільйони клонів × регулярні знімки пам'яті → терабайти даних щодня; потрібне ефективне зберігання метаданих і партиціонування      |
| **Velocity** (швидкість) | Безперервний потік запису з високою частотою; дані змінюються швидше, ніж їх встигають обробляти черги                              |
| **Variety** (різноманітність) | Структуровані метадані (clone_id, хеш, розмір, час) + великі бінарні образи пам'яті + службові події черги                   |

### Чому цей варіант обрано

1. **Класичний інженерний виклик DIA**: проблема тут не в бізнес-логіці, а в
   *інженерії даних* — прийом високих потоків, кешування, балансування навантаження,
   черги асинхронної обробки, масштабування без зупинки прийому.
2. **Чітко виділяються компоненти, передбачені курсом**: клієнти (сканери свідомості),
   бекенд (FastAPI-воркери), реляційна база даних (метадані бекапів), сервіси
   кешування (Redis) і балансування (Nginx) — саме ті елементи, що й потрібно
   спроектувати в архітектурі.
3. **Масштабованість теми на весь курс**: до кінця курсу проєкт можна нарощувати —
   черги, реплікація, партиціонування, горизонтальне масштабування воркерів,
   спостережуваність — усе вписується в цю саму предметну область.
4. **Мотивація**: цікавіше будувати систему, що «тримає» мільйони потоків, ніж
   черговий CRUD-сервіс.

## 2. Архітектура

Повний опис архітектури, схеми (mermaid) та діаграми послідовності взаємодії —
у файлі [docs/architecture.md](docs/architecture.md).

Коротко про шари:

```
Клон-сканери / Аналітична консоль
        │  HTTPS (REST API)
        ▼
Балансувальник навантаження (Nginx)
        │  round-robin розподіл
        ▼
FastAPI воркери (stateless, горизонтальне масштабування)
        │
        ├── Redis  — кеш метаданих + черга бекапів
        └── PostgreSQL — джерело істини (метадані бекапів)
```

## 3. Структура репозиторію

```
Synclone/
├── app/                    # код застосунку
│   ├── core/               # конфігурація та підключення до БД
│   │   ├── config.py       # налаштування (pydantic-settings, .env)
│   │   └── database.py     # engine, сесії SQLAlchemy, Base
│   ├── models/             # моделі (таблиці) бази даних
│   │   └── memory.py       # MemoryBackup — метадані бекапів свідомості
│   ├── main.py             # точка входу FastAPI (uvicorn app.main:app)
│   └── __init__.py
├── docs/                   # документація
│   └── architecture.md     # архітектурна схема та опис взаємодії
├── .env.example            # приклад змінних середовища
├── .pre-commit-config.yaml # конфігурація git-хуків якості коду
├── pyproject.toml          # налаштування ruff/black
├── requirements.txt        # залежності проєкту
└── README.md               # цей файл
```

## 4. Запуск проєкту

### 4.1. База даних PostgreSQL (Docker)

Контейнер сам створює користувача та базу — ручні SQL-команди не потрібні:

```bash
docker run -d --name synclone-pg \
  -e POSTGRES_USER=synclone \
  -e POSTGRES_PASSWORD=password \
  -e POSTGRES_DB=synclone \
  -p 5432:5432 \
  --restart unless-stopped \
  postgres:16
```

Перевірка готовності: `docker exec synclone-pg pg_isready -U synclone`

### 4.2. Запуск застосунку

```bash
# 1. Віртуальне середовище
python3 -m venv venv
source venv/bin/activate

# 2. Залежності
pip install -r requirements.txt

# 3. Налаштування підключення
cp .env.example .env   # DATABASE_URL уже вказує на контейнер synclone-pg

# 4. Запуск
uvicorn app.main:app --reload
```

- Swagger-документація: <http://127.0.0.1:8000/docs>
- Health-check: <http://127.0.0.1:8000/health>

Без файлу `.env` застосунок використовує локальний **SQLite** (`synclone.db`) як
fallback для швидкого старту; основний режим роботи — **PostgreSQL** із
Docker-контейнера `synclone-pg` (див. [docs/architecture.md](docs/architecture.md)).

## 5. Якість коду та pre-commit хуки

```bash
# Статичний аналіз та форматування
ruff check .
black --check .

# Встановлення git-хуків (після clone)
pre-commit install
pre-commit run --all-files
```

Хуки автоматично **блокують локальний коміт**, якщо є синтаксичні помилки
(перевірка ruff: `E999 SyntaxError`) або порушення стилю — виправлення
застосовуються автоматично (`ruff --fix`, `ruff-format`), після чого коміт
проходить успішно.
